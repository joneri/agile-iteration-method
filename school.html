FROM AN EMPTY PROJECT

Build Pocket Board with AIM

Pocket Board is a small task board for personal use. Add tasks, mark them complete and keep them after a page reload. Let your coding agent build it using the steps below, then use it as your example throughout the lessons.

1

Start in your AI tool’s chat

Create or open an empty project in your AI tool, such as Codex, Claude Code or GitHub Copilot. Start a new chat in that project and paste this message. Your agent can handle installation if it has terminal access.

Run this in the project’s terminal, then select your agent and project scope in the installer.

PROJECT TERMINAL

You do not need to know whether Python is already installed. Your agent checks Python 3 and Node.js/npm and helps you with anything missing. It verifies the installation before continuing. If your agent cannot run commands, it can guide you through the official Python installer and the Node.js installer. Reopen your agent session if the installed skill does not appear.

2

Set up orchestration and describe the project

For this example, use Ship / Auto. Ship means completing the agreed project before final acceptance. Auto lets the agent continue authorized work without asking you to relay routine decisions. Start by pasting this setup prompt into your coding agent’s chat:

AGENT CHAT · SET UP AIM

Use AIM in Ship / Auto. Act as my product owner and orchestrator.
Delegate delivery and arrange a separate reviewer.
You may approve delivery plans and resolve routine implementation questions
within the scope and resource limit we agree.
Confirm that scope and limit with me before implementation.
I retain scope changes, resource increases, publication and final acceptance.

Then describe the project in your next message. AIM uses this request to prepare the project context, requirements and work graph. In an empty repository, information about the technology and project starts as provisional and is checked as the project develops.

AGENT CHAT · DESCRIBE THE PROJECT

/aim start "Build Pocket Board: a local task board where I can add tasks, mark them complete and keep them after a page reload. Make it keyboard accessible and usable on a phone. No accounts or server. Plan the work and verify the result; I will give final acceptance."

If your agent does not support slash commands, write the same request in plain language and name AIM. New delivery plans use Native Graph engineering by default. AIM creates the graph from the requirements.

3

Agree the limits, then test the result

Agree the project’s scope and resource limit with the agent before implementation. With the setup above, the agent can approve delivery plans within that agreement, coordinate the work and handle routine implementation questions. It returns to you when it needs a reserved decision or presents the verified result for your acceptance.

Test Pocket Board by adding “Buy milk,” completing it and reloading the page. Try the same actions with the keyboard and on a phone. Accept the delivery when it meets the agreed criteria; otherwise describe what needs correcting.

Use /aim ui to inspect Stories and evidence or /aim status in chat. Use /aim continue to resume authorized work. A continue command does not approve a pending decision.

2

Describe a change in the current application

Name the behavior you need and the constraints AIM should preserve.

EXISTING REPOSITORY · AGENT CHAT

/aim start "Improve checkout recovery in this existing application. Customers must be able to check a delayed payment confirmation without placing a duplicate order. Use the current stack, architecture and test tools. Preserve existing checkout behavior and unrelated local changes. Verify the recovery journey and relevant regressions. I retain scope changes, publication and final acceptance."

3

Build verified project knowledge

AIM inspects relevant code, project instructions, build metadata, tests and maintained documentation. Calibration records the stack, architecture, conventions, verification commands, important code areas and risks, with sources and recheck triggers. Uncertain facts stay provisional.

With repository sharing, compact knowledge lives in aim.profile.yaml. Other setups can use permitted external storage or session context. Existing verified knowledge is reused and affected facts are refreshed when the project changes.

4

Equip the four canonical roles

AIM uses that knowledge to prepare relevant role responsibilities, skills and checks. Where the setup includes it, aim.roles.yaml holds the project-specific configuration.

The roles stay the same; their project expertise changes.
RoleWhat it needs for this project
PO · Product OwnerUsers, product purpose and domain rules to frame outcomes and priority.
TDO · Technical Delivery OwnerArchitecture, dependencies and verification methods to plan Stories and validate delivery.
DevThe affected framework, implementation conventions and development skills to build the approved change.
ReviewerRequirements, regression risks and testing skills to independently challenge material changes.

Each role has a bundled engineering skill. Project skills are selected from actual available instructions and read before use. Missing capabilities are reported with a fallback. Native role files are prepared where permitted; the coding platform must load them and may need a session reload.

Review the proposed scope, checks and resource limits before implementation. The default Strict mode keeps plan approval with you. Dev builds, a separate Reviewer checks material work, and TDO validates the integrated result before PO assesses it. Final acceptance stays with you unless explicitly delegated.

PROFESSOR AIM / CHECK THE PREPARATION

Ask which areas AIM inspected, what it verified, which role skills it can actually read, what remains uncertain and how it will test your change. A framework name or a written agent file alone does not establish expertise or a running specialist.

REFRESH WHEN THE PROJECT CHANGES

Normal starts already include needed preparation. Use /aim calibrate-repo for a separate knowledge refresh, then /aim configure-agents to refresh affected roles and skill bindings. AIM preserves user-edited settings and the selected storage policy.

LESSON 1 / INTENT

Describing requirements

An intent describes what you want to achieve and who will use the result. Explain the main actions the user should be able to perform, along with relevant constraints. You can start with a rough idea and work out the details with AIM.

AIM groups related outcomes into Epics and describes individual user needs as Stories. Each Story has acceptance criteria: observable conditions used to decide whether the work is complete.

POCKET BOARD

“Tasks and their completed state must remain after closing and reopening the tab.” This requirement tells the planner that the application needs to save both the task text and its state.

For Pocket Board, agree that tasks are saved in the same browser, users can add and complete them with a keyboard, and the interface works on a phone. Accounts and cloud synchronization are outside this delivery. Also state any required technology, data restrictions or resource limit.

PROFESSOR AIM / QUALITY REQUIREMENTS

Include quality requirements in the initial agreement so they appear in the plan and its checks. For example, “keyboard accessible” means the reviewer needs to check focus, navigation and task actions using the keyboard. If response time matters, state the operation and an acceptable time.

Before you move on
  • Can you describe a real user completing the main action?
  • Have you named what must survive failure or a restart?
  • Are the scope, quality expectations and resource limits clear?

For Pocket Board: reload after a change, submit an empty task and use only the keyboard. These are concrete checks the plan can preserve.

LESSON 2 / GRAPH ENGINEERING

Planning and assigning work

A work graph records the activities needed for a delivery, the dependencies between them, who performs each activity and how the result will be checked. AIM selects a suitable graph from your requirements or validates one you provide. The same agent can perform several activities.

  1. Review the planRequirements, criteria and limits
  2. Implement the task boardAdd a task, complete it and reload
  3. Review and testCheck behavior against the requirements
  4. Assess the resultAccept the delivery or request a correction

In this tutorial, the agent you talk to is the product owner and orchestrator. It is responsible for outcomes, priorities and follow-up, and delegates delivery to another agent. The delivery coordinator plans the Stories and maintains the delivery record; it may also implement the work. A separate reviewer examines the result against the requirements. These responsibilities are established by the setup prompt before the project request.

POCKET BOARD

Start by checking that a task and its state survive a page reload. Then develop the rest of the interface. Assign task state and saving to the same implementer because those parts need to work together.

PROFESSOR AIM / WHAT TO INCLUDE IN AN ASSIGNMENT

An assignment should state what to implement, which files may change, which interfaces it must use and how to check the result. For example: “Save the task list and completed states in this browser. Check that both survive a reload. Report the changed files and the check results.” The coordinator then checks whether the assignment is complete.

When does parallel work help?

Use it when agents can change separate files and have agreed how their parts connect. Research and independent review can often proceed separately. If two tasks depend on the same code, dividing them between agents can add handoffs, repeated context and integration work.

The coding platform must support starting agents and exchanging messages for this delegation to work. The coordinator should report which agents it actually started and whether their replies were received.

LESSON 3 / MODEL ALLOCATION

Choosing models and reasoning levels

Model choice depends on the work. A more capable model can help with ambiguous requirements, difficult planning or diagnosis. An implementer may be able to use a less costly model when its assignment is well specified. The reviewer needs enough capability to evaluate the relevant behavior and risks. It can use the same model as the implementer, provided it is a separate agent.

AN OPTIONAL CODEX SETUP

Coordinator
GPT-6.1 Sol · Extra High
Plans, assigns, follows up and integrates.
Implementer
GPT-6 Luna · Max
Builds the bounded assignment and returns evidence.
Reviewer
A separate agent
Independently checks requirements, behavior and regressions.

This is one suggested setup. Other combinations of models, reasoning levels and responsibilities may work better depending on the task, its complexity and the resources available.

Select only models and reasoning levels your account and coding platform actually offer. Set the coordinator in the host’s model controls; ask it to use the chosen implementer when delegation controls support that. A prompt cannot create a missing model, change a host limit or guarantee that a requested setting was applied. Have the coordinator report the actual allocation.

PROFESSOR AIM / CHOOSING A REASONING LEVEL

Reasoning levels affect the effort a model spends on a task. A higher level may help with difficult planning or diagnosis and may also increase time and resource use. For Pocket Board, implementing an agreed task-saving format may need less reasoning than diagnosing why completed tasks disappear after a reload. Include planning and supervision when comparing the total resource use.

Model controls and availability change. Check OpenAI’s current Codex guidance and your host’s actual selector. This is an optional example; AIM also works through its Claude Code and GitHub Copilot adapters.

LESSON 4 / AUTHORITY

Delegating decisions

By default, you own approval and acceptance. You can explicitly delegate particular decisions to an agent within a named outcome and resource boundary. AIM records the actual owner and mandate in the delivery plan; “be my orchestrator” and Auto mode alone do not grant acceptance.

For Pocket Board, you can let the coordinator resolve routine implementation questions while you retain changes to scope, budget and final acceptance:

The setup prompt in the quick start delegates plan approval and routine implementation decisions. It keeps changes to scope or resources, publication and final acceptance with you. State any additional decisions you want to retain before work begins.

Different decisions need different authority
DecisionWhat must be clear
Internal implementation choiceStay within approved requirements, write scope and resources.
Approve a delivery planThe human decides or explicitly delegates approve.
Accept a verified deliveryThe human decides or explicitly delegates accept. Required human tests remain binding.
Grant further work attemptsSeparate orchestrate permission and a positive cumulative maxAdditionalAttempts cap. The human mandate must authorize it.

PROFESSOR AIM / HANDLING QUESTIONS FROM OTHER AGENTS

From AIM 4.8.2, a coordinator routes internal decision requests to the owner named in the delivery plan. For Pocket Board, the implementer might reach the agreed work-attempt limit while tasks still disappear after a reload. It asks the delegated owner whether further work can be authorized. The owner must receive the question and answer within its mandate. If the choice needs more authority, such as a budget increase the owner cannot approve, it asks you.

Ship, Loop, Strict and Auto

Ship finishes the agreed outcome before final owner acceptance. Loop delivers useful increments and uses actual owner feedback to choose subsequent work. Both retain quality and independent review.

Auto continues within existing authority. In this guide, the setup prompt explicitly delegates plan approval within an agreed scope and resource limit; final acceptance stays with you. Selecting Auto alone does not delegate those decisions.

Strict asks the designated owner for plan approval and acceptance. Use it when you want to make those decisions yourself. It is AIM’s default when you have not selected another mode. The choice concerns decision authority, rather than the user’s experience level. Both modes retain the agreed quality checks and independent review.

Existing approved deliveries keep their frozen policy after an upgrade. Delivery acceptance does not grant separate Epic closure.

LESSON 5 / RESOURCES

Tracking resource use

When comparing two ways of working, use the same requirements and quality criteria. Record the resources used for planning, implementation, subagents, review, integration and corrections. This shows the total cost of the delivery, including any additional work needed to fix defects.

WHAT TO RECORD

Before work starts
The outcome, quality criteria, approved model pool, maximum concurrency and total resource ceiling.
During the work
Actual host usage where available, elapsed time, attempts, correction rounds and remaining budget.
After the delivery
Total delivery cost and time, verified behavior, defects and owner assessment. Keep unknown values visible.
POCKET BOARD

Ask for one author and a separate reviewer. Set a resource limit you can actually monitor. If persistence fails repeatedly, the coordinator should use the evidence to choose a different bounded next step.

PROFESSOR AIM / UNITS AND LIMITS

State what each limit measures. An attempt cap limits the number of work starts. A token cap, a subscription allowance, elapsed time and a money budget measure different things. If the coding platform cannot report a requested measure, agree on an alternative before relying on that limit. For Pocket Board, permission for two further attempts to fix task saving limits the number of work starts; it does not specify how much those attempts will cost. Keep unavailable usage figures marked as unknown and preserve the agreed resource boundary.

Ways to reduce unnecessary work
  • Reuse current repository facts and evidence when their sources still match.
  • Send each agent only the context its assignment needs.
  • Keep coupled implementation with one author.
  • Verify the first working core before expanding it.
  • Reassess repeated failure against the real outcome and remaining resources.
  • Change the next action when the evidence changes; a heartbeat or new session does not renew the budget.

AIM’s Cost Control profile reduces context and narration. It preserves material independent review and the agreed quality bar. It is separate from Ship/Loop, Strict/Auto and host model settings.

LESSON 6 / EVIDENCE

Testing and accepting the result

The implementer returns a working candidate and its checks. The separate reviewer examines the original requirements, changed behavior, relevant regressions and actual results. The coordinator resolves findings and validates the integrated journey before presenting it to the owner.

  • Saving task state: add “Buy milk,” complete it and reload. The task and completed state remain.
  • Empty input: submit an empty task. The board stays usable and explains what to do.
  • Keyboard use: add and complete a task with the keyboard. Focus stays visible and follows a useful order.
  • Phone layout: run the version being presented on a phone-sized screen. Review evidence must match that version.

Ask for the changed files, instructions for running the application, check results, reviewer findings and any remaining limitations. Test the relevant actions in the running application as well as reading the reports. If a check fails, request a correction against the same agreed criteria.

PROFESSOR AIM / GIVING FEEDBACK AFTER TESTING

During your test, describe what you did, what happened and what you expected. For example: “I completed a task with the keyboard. Afterwards I could not see which control had focus.” Identify the version you tested so the coordinator can reproduce the problem and check the correction.

Continue, learn and keep guidance current

Use /aim continue to resume from the real checkpoint. Use /aim remember-repo for durable project facts. AIM recalls relevant shared learning during delivery; no routine reflection command is needed.

Use /aim upgrade for an existing AIM installation. An upgrade preserves approved scope, history and accepted evidence; it does not grant a new mandate. Check the release notes for changes before starting new work.
