SHORT DESCRIPTION
Agile Iteration Method (AIM) is an open-source method and tooling for AI-assisted software development. Describe the result you want. Ship takes the agreed product through planning, implementation, independent review and real verification before final acceptance. Choose Loop when recurring owner feedback should shape the next useful Done Increment. AIM UI is the local control room for Stories, the selected delivery, dependencies and evidence. Graph engineering connects responsibilities, prerequisites and proof; the Graph view makes those recorded relationships visible.

CURRENT CAPABILITIES
- Open AIM UI with /aim ui to inspect User Stories, the selected delivery, Graph, review evidence and recorded progress alongside your coding agent. The UI remains Beta; copying a handoff does not start agents or grant approval.
- Ship is the default: complete the agreed product before final acceptance. Choose Loop for useful Done Increments with recurring owner feedback.
- Use Graph engineering to connect ownership, dependencies, delivery and independent proof. An agent owner can give feedback and decide in Strict Loop only under an explicit human mandate and its permitted delivery decisions.
- Use AIM Graph to see delivery dependencies, current activity proof and blockers. Copy bounded assignments with role skills and file responsibility. Changed inputs identify the affected work and evidence that need correction.
- Agree quality goals before implementation and test the first working core before building around it. A separate reviewer challenges a material core with an independent example.
- Verify the real user journeys through the delivered application. Keep raw observations behind the assessment, including complete-result time when it matters.
- Maintain a map of important user journeys and a runnable verification route so later changes can reuse the right checks.
- Reuse repository knowledge, compact confirmed checkpoints and still-applicable results. Existing approvals and answers stay bound to their scope.
- Recall relevant shared lessons during planning, review and diagnosis. Share verified reusable corrections with existing proof during ordinary delivery.
- Select Stories across Epics, review a coherent increment and keep user acceptance explicit. Closing an Epic remains a separate decision.

EXAMPLE
A customer needs reliable booking confirmation. A support specialist needs a useful failure reference. Those Stories can belong to different Epics and be delivered together. The plan includes delayed responses, repeated requests and the complete confirmation journey, with retained results for review.
