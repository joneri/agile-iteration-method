   from manifest.json and tell me if a session restart is needed.

   Reuse existing authorized AIM work and repository knowledge. Within the same start,
   calibrate missing or stale repository knowledge from the intent, then configure
   missing or stale project agents and their available skills. Preserve existing files,
   user-edited agent settings and AIM history.

   delivery, dependencies and evidence. Explain what Graph records and when the
   designated owner gives feedback or decides.

Open a local control room alongside your coding agent. Follow User Stories, inspect the current delivery and use Graph to see dependencies, blockers and the evidence behind the next step.

Choose how feedback shapes the delivery

Ship the product. Or build through feedback.

Ship completes the agreed product before final acceptance, including the experience your users need. Choose Loop when you want to assess useful Done Increments and use that feedback to decide what comes next. Both include independent review, verification and correction.

Example product intent

/aim start "Build a booking app where customers can find available times, book appointments and manage their bookings."

  1. Agree the outcome.

    Describe who the product serves, what must work and how good it needs to be. Agree the scope and resource boundary. Ship is the default; select Loop when recurring owner feedback should guide the next increment.

  2. Plan connected work.

    AIM turns the outcome into User Stories and a coherent delivery plan. Graph engineering makes responsibilities, dependencies and required evidence explicit. AIM UI keeps the selected work in view.

  3. Build, challenge and verify.

    Check the first working core early. A separate reviewer challenges the implementation, and validation checks the real user journeys. Failed checks send the work back for correction.

  4. Assess the agreed result.

    Ship presents the complete agreed product for final acceptance. Loop presents each verified increment to its owner for assessment and feedback. An owner can be human or an agent with explicit human delegation.

Ship and Loop set the delivery rhythm. Strict/Auto controls approvals separately. The agreed quality bar applies to both.

Repository-aware development

Your agents should know the project they are building.

AIM gives agents reusable project knowledge, a focused view of the code and skills suited to their roles. Each task starts with relevant facts, clear responsibilities and checks for the result you want.

Repo profile

Keep project knowledge between sessions.

Calibration records your stack, conventions, build and test commands, important code areas and risk zones in a repository profile. The next session can reuse those facts instead of discovering the project from scratch.

aim.profile.yaml holds reusable knowledge. AIM checks the affected facts when the project changes.

Localities

Give each task the context it needs.

Localities map areas of your codebase to their responsibilities, files, tests and dependencies. A maintained map of user journeys connects important behavior to runnable checks, so later work can reuse the same verification route.

Compact checkpoints and unchanged results are reused when their scope and dependencies still match. New risks or changed behavior trigger fresh checks.

Tool & MCP efficiency · New in 4.7.4

Use less tool context. Keep the evidence.

AIM finds tools when they are needed and uses the capabilities your coding platform actually exposes. Where supported, code filters and combines large tool responses before they enter model context. Small calls stay simple.

Sources, contrary findings and partial errors stay visible, with raw evidence available for review. When native support is missing, AIM uses bounded ordinary calls. Your approvals and permissions still apply. Actual token and cost savings depend on the task and platform.

Graph engineering

Connect ownership, work and proof.

Make it clear who owns the outcome, what depends on what, and which evidence or feedback unlocks the next step. Your agent can coordinate AIM delivery while a separate reviewer checks the implementation. In Strict Loop, an explicitly delegated owner agent can assess each increment and give feedback.

Graph engineering is the working approach. The Graph view in AIM UI makes recorded dependencies, activity evidence and blockers visible. Copying an assignment prepares the next handoff; it does not start agents.

Talk to one delivery coordinator. Give it the outcome and boundaries; let it organize the work and bring the evidence back to you.

Act as my AIM delivery coordinator and primary point of contact.
Use Agile Iteration Method to deliver this outcome:

[Describe the benefit users should receive and the context in which
they need it.]

Success means:
- [A concrete, observable outcome.]
- [An important quality requirement.]
- [A constraint that must be respected.]

Coordinate delivery through Graph engineering:

1. Establish the relevant facts.
   Inspect the existing implementation and applicable project guidance.
   Reuse verified knowledge and available project skills. Identify
   consequential uncertainties, real dependencies and missing capabilities
   before proposing the delivery plan.

2. Build the smallest useful delivery graph.
   Connect activities to AIM Stories, acceptance criteria and user value.
   Define each activity's result, required inputs, prerequisites,
   responsible agent, write boundaries and verification.
   Keep simple work simple; an activity does not require its own agent.

3. Allocate work proportionately.
   Keep cohesive implementation with one responsible author. Delegate
   bounded investigations and independent review when useful.
   Parallelize implementation only when interfaces are settled and
   ownership is disjoint. Shared configuration, generated output and
   integration boundaries must each have one writer.

4. Give clear assignments and follow them through.
   Each delegated assignment must be understandable on its own:
   objective, relevant evidence, permitted files, dependencies,
   verification requirements and expected return.
   Tell agents that others share the codebase and that they must preserve
   others' work. Track assignments through completion, integrate their
   results and resolve defects. You remain accountable for the whole
   delivery and its evidence.

5. Let evidence determine the next action.
   Verify the first working core before costly expansion. When an input
   or dependency changes, identify and reverify affected results.
   Preserve failures, counterevidence and unresolved uncertainty.
   Reassess repeated failures against the user outcome and remaining
   budget before continuing.

6. Review and verify the complete outcome.
   Use a separate reviewer for material changes. A role switch within
   the implementing agent is self-review.
   Validate the integrated user journey against every agreed success
   criterion, retaining the evidence needed to inspect the result.
   Report unavailable independent review as an unresolved requirement.

Authority and resources:
- Delivery style: Ship. Execution mode: Strict.
- Follow AIM's existing roles and approval gates. You alone maintain
  this delivery's AIM runtime state.
- Maximum concurrent agents: [N], including you.
- Total resource limit across all agents: [limit and accounting basis].
- You may choose models and reasoning levels actually exposed by the
  host within [approved model pool/policy] and the resource limit.
  Make choices proportionate to task risk and required evidence.
  Where controls are unavailable, inherit configured defaults.
- Distinguish observed resource use from estimates and unknown values.
  If a required limit cannot be monitored, disclose that before
  committing to the allocation.
- Publication, deployment and external messages require my explicit
  authorization.
- I retain scope and budget decisions and final product acceptance.

Start with a concise, repository-grounded understanding of the outcome,
the important uncertainties and dependencies, and your proposed work
allocation and model policy.

Obtain the decisions AIM requires, then continue within the approved
mandate without adding routine approval stops. Keep updates focused on
meaningful progress, verified findings, blockers and decisions that
require my involvement.

Project agents & skills

Configure specialists for your stack.

Give each role the project knowledge and skills its work needs. /aim configure-agents prepares specialists for Codex, Claude Code or GitHub Copilot.

A role defines responsibility. An owner agent also needs your explicit mandate for the product decisions it may make.

AIM recalls relevant shared lessons while planning, reviewing and diagnosing failures. Verified reusable corrections feed that shared advice during ordinary work. Focused context and reuse are designed to avoid repeated effort; their cost benefit depends on the work.

AIM Discuss

Talk to your code. Understand what you can build next.

Ask how a feature works, why the code is structured a certain way or what a proposed change would affect. AIM follows the relevant code and project context to help you understand the answer and weigh your options.

Use Discuss in your coding agent’s chat to explore an idea before committing to it. It reads and explains the project without changing the code or starting a delivery.

Try a question about your project

/aim discuss "How does booking cancellation work, and what would need to change to support rescheduling?"

Follow up, challenge an assumption or explore another approach. When you are ready to build, turn the decision into an intent with /aim start.

Already using AIM?
