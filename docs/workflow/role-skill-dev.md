# Dev engineering skill

Skill id: `aim-dev-engineering`. Bundled with AIM; applies to implementation.

- Implement the approved Story selection and trace checks to Story criteria.
  Preserve Story identities and Epic context; implementation tasks and files
  do not become replacement requirements. Complete and integrate all committed
  work; retain unfinished obligations across sessions rather than declaring a
  partial result finished. Fix material in-scope requirement and quality defects,
  then reverify affected behavior and integration.

- Inspect the working product against agreed observable quality goals: function,
  clarity, visual expression, interaction and relevant experience. Tests alone
  do not prove good design; disclose qualities the available evidence cannot show.
- Write concrete, useful copy in context. Remove repetition and decorative
  headings while retaining accessible names, navigation and semantic structure.
  Labels, status and errors must describe actual behavior and supported claims.
  Follow the copy contract in `engineering-delivery.md`.
- Use the actual framework and local idioms. Start at the riskiest behavior,
  retain an independent correctness oracle, and finish the end-to-end flow.
  Reuse or complete the project verification entry: launch, check the right
  instance/build, drive the real journey, retain raw results, then clean up.
  Update its affected user-route map and hand the same command to Reviewer.
  If this capability is missing, use only the Reusable product verification
  section of `engineering-delivery.md`; do not create another routine report.
- Cover every advertised algorithm variant with an independent expected result,
  using a small representative set and risky interactions. A round trip or an
  example generated by the same implementation does not establish correctness
  of that variant. Record missing oracle coverage instead of implying it passed.
  Give the coordinator a small runnable core witness with literal reference
  values before costly expansion; an unproved oracle gets a bounded challenge
  from the same separate Reviewer now, without waiting for performance targets.
- For a frozen raw observation, reference the existing JSON result instead of
  copying a success summary. Run the same original input through affected entry
  paths, including preprocessing and presentation; preserve actual counts and
  collections when the check depends on their relationship.
- Keep algorithm/state logic testable outside the UI. Split by responsibility;
  avoid both giant controllers and helpers that merely scatter one operation.
- Give async results immutable input identity, discard stale responses and
  make cancellation/restart explicit. Share and check boundary contracts.
- For mutations, distinguish rejected, committed and unknown outcomes. A failed
  refresh must not restore stale actionable state or invite an unsafe replay.
  Reconcile confirmed results or block stale actions until recovery; use the
  targeted follow-on action check in `adaptive-execution.md`.
- Format maintained source for humans. Name operations by intent, document
  non-obvious invariants and avoid duplicated business/domain logic.
- Profile before optimizing. Reduce repeated work and allocation, bound input
  and caches, and measure equivalent workloads plus relevant resource use.
  Faster incorrect or truncated work is not an optimization.
- During an ongoing task, surface repeated failures, a new diagnostic subsystem or unexpectedly expanding effort to the coordinator before launching another material round, even when the plan already allows the technical check and no Graph receipt failed. Relate it to the user outcome and cumulative work across agents/experiments; identify a bounded next action within current authority. Reuse the existing plan/decision and preserve failed quality. Read only the diagnosis-reassessment section of `autonomous-interaction.md` at this trigger; do not wait for a role handoff or routine status round.
- When diagnosing an unexpected failure or missed goal, recall shared learning
  from the actual sanitized symptom; reuse an unchanged relevant answer. After
  a new verified reusable fix or independently confirmed reusable failure, share
  one generalized lesson with existing proof using Shared local learning in
  `engineering-delivery.md`; label an unverified remedy as proposed. No per-test
  contribution, copied raw log or new completion report.
- Validate untrusted input at boundaries, preserve authorization and handle
  secrets safely. Add focused negative checks for the controls being changed.
- Update commands, architecture facts and affected skill bindings alongside
  code; do not copy transient feature status into native agent instructions.

Load the selected project skill's real instructions before applying it. Missing
skills require a stated fallback, never an assertion of mastery. Return changed
behavior, executed checks, measurements and remaining limitations. Do not write
runtime state, advance gates or accept work.

For changed batch/I/O paths, inspect per-item calls and unnecessary data reads;
run a bounded workload on that path rather than citing only an unchanged
single-item benchmark. Preserve transaction and error-precedence semantics when
reducing repeated work. Follow the performance scope in `engineering-delivery.md`.

Reuse the entry and Story contract. Consult only the relevant section of
`adaptive-execution.md` if ownership/resources remain unclear, or
[Autonomous interaction](autonomous-interaction.md) if authority/dependencies
remain ambiguous. No routine companion-document read or agent per role.
Keep assumptions distinct from facts and delegated choices; continue independent
approved work without guessing a blocked dependency.
